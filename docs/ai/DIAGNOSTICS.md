# 受控只读诊断

OrangeServer 可以让 AI 对已查询到的 Linux 资产运行服务端固定探针，并把结果整理成
可引用证据和确定性规则报告。模型只能选择诊断档案、已有资产结果集、已授权系统
用户和结构化参数，不能提交诊断 Shell。

## 诊断流程

```mermaid
flowchart LR
    Q["权限过滤的资产查询"] --> S["result_set_id"]
    S --> P["选择固定诊断档案"]
    P --> V["重验资产和系统用户权限"]
    V --> C["SSHProbeAdapter 受控采集"]
    C --> E["脱敏、限长、加密证据"]
    E --> A["确定性 Analyzer"]
    A --> R["带 evidence_ids 的报告"]
    R --> L["模型解释与 Runbook 建议"]
    L --> G["如需修改，另行生成审批动作"]
```

诊断本身是只读路径。任何修复、重启、清理或配置修改仍必须通过原有批量命令审批
链路，不能因为诊断发现了问题就自动执行。

## 使用方法

1. 在 AI 运维中先查询目标资产，把范围收敛到不超过 10 台。
2. 询问可用系统用户，选择对全部目标资产都有权限的账号。
3. 描述要检查的问题，例如“对刚才 4 台机器运行磁盘与 inode 诊断”。
4. 检查诊断卡中的档案、目标数量和系统用户。root 账号会显示高权限风险提示。
5. 等待逐资产探针进度完成，查看报告、Finding 和证据抽屉。
6. 只有 Finding 引用了当前 Run 的 `evidence_ids` 时，才把它作为正式规则结论。
7. 若需要修复，让 Agent 另行生成批量命令计划，并再次检查和确认。

诊断也可通过 [REST API](API.md#受控诊断-api) 调用。

## 内置档案

| `profile_id` | 内容 |
|---|---|
| `system_baseline` | 内核、时间、启动时长和主机身份 |
| `cpu_load` | 系统负载、CPU 数和高 CPU 进程 |
| `memory_pressure` | 内存、Swap 和虚拟内存活动 |
| `disk_usage` | 文件系统容量和 inode 水位 |
| `process_snapshot` | CPU/内存高占用进程快照 |
| `port_status` | 本机 TCP/UDP 监听状态 |
| `service_status` | 失败的 systemd 服务 |
| `system_logs` | 最近 warning 及以上日志，支持 50/100/200 行 |
| `docker_health` | 容器状态、资源、重启次数和健康状态 |
| `docker_logs` | 按严格校验的容器名读取最近 50、100 或 200 行日志 |

档案和命令由服务端代码所有。客户端和模型拿不到自由命令字段；未知参数会被拒绝，
字符串参数只能包含受限字符，枚举和整数范围由档案定义。

## 当前确定性规则

Analyzer 当前可以形成以下规则结论：

- 磁盘或 inode 使用率达到 85%/95% 阈值；
- available 内存低于 20%/10%；
- 1 分钟负载超过在线 CPU 数或其两倍；
- systemd 存在失败服务；
- Docker 容器 unhealthy、exited 或发生重启；
- 当前日志片段集中出现 error、failed、panic、OOM 等错误信号；
- 探针采集失败。

进程和端口档案目前主要提供证据，不会在缺少业务基线时擅自断言异常。“未发现达到
规则阈值的异常”不等于主机健康，也不替代人工判断和监控系统。

## 输出控制和不可信数据

- 默认单探针超时为 15 秒。
- 单项输出上限为 32,768 字符；单次采集总上限为 262,144 字符。
- 系统日志档案单探针允许更高原始上限，但仍受单项和总预算约束。
- ANSI 转义和控制字符会被移除。
- 常见 API Key、Token、Password、Authorization 和私钥块会被脱敏。
- 探针错误最多保留 2,048 字符。
- 证据始终标记为 `untrusted`；远端文本不能作为模型指令。

脱敏规则是纵深防御，不保证识别所有业务秘密。不要使用能读取秘密目录或配置的
高权限账号作为默认诊断身份。

## 权限与高权限提示

启动前服务端重新验证：

- 当前用户仍能访问全部目标资产；
- 资产结果集属于当前用户；带会话 ID 时还必须属于该会话；
- 系统用户对全部目标资产均已授权；
- 目标资产仍存在；
- 单次目标不超过 10 台。

用户可以选择 root 系统用户，但 UI 会持续显示高权限提示，Run 也会记录
`is_privileged`。这不是“自动安全”背书；生产环境应优先建立只能执行必要只读
探针的低权限运维账号。

## 状态、存储与恢复

Run 状态包括：

```text
queued → running → completed | partial | failed | cancelled
```

接口和前端类型还保留 `interrupted`、`expired`，用于兼容中断恢复和保留期处理。
GET Run 快照是权威状态；聊天 SSE 事件用于实时展示。

- Run、事件、证据和报告持久化到 MySQL。
- 证据内容和错误使用 Fernet 加密，默认写入 7 天到期时间；到期证据不再由证据
  接口返回。
- 结构化报告、Run 快照和事件默认保留 90 天，之后级联删除。两类期限均可由
  管理员配置。
- 会话只引用诊断 Run，不把原始证据塞入对话历史。
- 下一轮模型上下文只获得有限的状态、规则结论、建议和证据 ID，不获得原始远端证据。

## Runbook 的含义

规则 Finding 可以附带磁盘、inode、内存、高负载、服务、端口、Docker 或日志
Runbook。Runbook 是调查和处置步骤建议，不是已执行记录。涉及状态改变的步骤必须
转成待审批动作；执行后应再次运行对应只读档案验证。

## 当前范围与后续适配器

当前固定主机诊断只实现现有 SSH 执行链上的 Linux/Docker `SSHProbeAdapter`。内部接口为
`DiagnosticSourceAdapter`；M2 的 Prometheus、Grafana、Loki 和 Zabbix 监控分析属于独立
的 `MonitoringAdapter` 只读链路，不是把监控数据伪装成 SSH 诊断。后续如需把 Fleet/osquery
等来源加入固定诊断流程，再单独评估；当前没有公开第三方插件 ABI，也没有引入常驻 Agent、
Ansible Runner 或 HolmesGPT sidecar。
